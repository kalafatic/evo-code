Overview

EVO-Code is a native AI coding harness: an LLM-driven coding agent that plans, executes tools (git, build, test, JDT analysis, refactoring) and produces reviewed changes in a workspace. It is one product with three client faces over a single backend:

  • RCP IDE — Eclipse RCP desktop application (views, editors, console, activity).
  • Web IDE — the served web interface (this server; open the site root).
  • Headless server + CLI — the dcode-headless launcher with a command-line interface against the same /api/v1 endpoints.

All three faces share the same application core: sessions, workspaces, repositories, runtimes, models, agents, tool calls and reviews are persisted on the server and never duplicated per client.

Default HTTP port: 48080 (family convention 8x80 + product offset; the actually bound port is reported by /api/v1/ports and published as the dcode.server.port system property).

Getting Started

  1. Start the backend. Run the headless launcher (scripts/run-headless.sh) or open the RCP IDE, which embeds the same server in local mode.
  2. Connect the IDE. In RCP, File ▸ Connect to Runtime… shows the current endpoint. Local mode targets the embedded server; set a remote URL to reach an independent headless server (plus an optional bearer token).
  3. Register a runtime. Open Window ▸ Runtime Explorer (or the Runtimes page of the web UI) and use Add… or Scan local… to register an ENR, Ollama or OpenAI-compatible endpoint. Use Test Connection and check the model list below the runtime.
  4. Create a workspace. Workspaces group repositories (git worktrees) and sessions. The Workspace Explorer creates and manages them; repositories can be added, cloned and inspected (status/diff/commit/pull/push) from its context menu.
  5. Start a session. Sessions view / page ▸ New session…, choose a workspace (and optionally runtime/model). Open the session to make it active.
  6. Submit a task. In the Chat/AI Workspace view (or the web session tab) describe the coding task. Execution runs on the backend; watch tool calls in the Activity view and the structured console, and review the resulting changes in Changes.
  7. Direct chat. The Direct Inference Chat (Window ▸ Direct Inference Chat, or the web "Direct chat" button) talks to a runtime/model without a coding task — useful for model experiments.

Context Help

Press F1 in any view to jump straight to its section.

Workspace Explorer

The left tree shows workspaces, their repositories and the file tree. Context menus offer git operations (status, diff, commit, pull, push), opening files in the source editor and the JDT AST summary for Java files. Repository operations are policy-enforced on the backend: READ_ONLY repositories reject mutations.

Sessions

Persisted sessions per workspace. Open makes a session the active session and starts its live event stream; running sessions offer Cancel execution. Sessions can be renamed and deleted (web UI / CLI). Open executions are reconciled to FAILED on restart — they cannot be resumed.

Chat / AI Workspace / Direct Inference Chat

The chat transcript shows the session conversation (roles you / agent / tool / system); messages stream in over SSE. The context menu offers Copy (selection or all) and Copy Code (the fenced code blocks of the text). The AI Workspace view additionally submits tasks or direct prompts; the Direct Inference Chat streams tokens from the selected runtime/model without a coding task (its Retry button re-generates the last direct response client-side).

Console

The structured console logs every operational entry (categories SYSTEM…EVENT) into a bounded buffer that survives filtering, pausing and clearing — diagnostics are never discarded. Toolbar and context menu: Clear (hides entries from view, buffer kept), Copy (selection or visible text), Save Output… (exports the complete buffer to a .txt/.log file), plus pause/auto-scroll and the toolbar's Copy all / Export….

Runtimes & Models

Runtime registrations (ENR, Ollama, OpenAI-compatible) with live availability: test the connection, refresh/enable/disable, set the platform default, edit or remove a registration. The model list under each runtime is real provider discovery. Model capabilities (load/unload/ pull) are exposed only when the runtime supports them. Double-clicking a model in the Runtime & Models view sets the platform default runtime/model.

Providers

Read-only listing of the LLM providers the backend is configured with (a view over the runtime registrations) plus Test connection against the first provider.

Agent Explorer

Built-in and custom coding agents with role, system instructions, tool permissions and preferred runtime/model. The default agent is bound to new sessions. Built-in agents are immutable; custom agents can be created, edited and deleted (persisted on the backend, shared with the web UI).

Activity

Live tool calls of the agent execution: tool name, state, timing and error messages.

Changes

The git state of the session workspace: changed files and the unified diff, straight from the backend repository engine.

CLI Commands

Run dcode-headless <command> against the same backend as RCP and Web. Commands may be written plain or slash-prefixed (/status); leading slashes are normalized. With no command and an interactive terminal the launcher starts a evo-code> REPL reading the same commands until /exit or EOF; without a terminal it runs the server in the foreground (daemon mode).

status [runtime]      backend readiness and lifecycle stages
                    (with "runtime": runtime registrations summary)
runtimes             runtime registrations with live availability
providers [list]     provider listing
providers test <id>  test one provider connection (POST /api/v1/providers/<id>/test)
models [list]        unified model catalogue
models show <id>     details of one model of the catalogue
sessions [list]      sessions per workspace
sessions show <id>   one session with its current state
sessions delete <id> delete a session (DELETE /api/v1/sessions/<id>)
logs [show]          recent buffered log entries of this process
web                  open the web interface in the system browser
terminal [dir]       open a system terminal (optionally in a directory)
agents list          agent list with the default marker (GET /api/v1/agents)
config show          effective config summary: port, data dir, workspaces dir (no secrets)
start                verify/start the EVO-Code server on the configured port
stop                 stop the EVO-Code server process on this port
restart              stop the server (start it again afterwards)
exit                 leave the interactive REPL (no-op as a launch argument)
help [topic]         this help, or the help of one command
                    (/help /status /start /stop /restart /web /terminal /models
                     /sessions /providers /agents /config /logs /exit — slash
                     forms are equivalent)

Diagnostics

  • GET /api/v1/status — readiness flag and lifecycle stage states.
  • GET /api/v1/ports — the actually bound service ports and their states (port conventions: EVO-Code 48xxx).
  • GET /api/v1/health — application identity, version and readiness (used by the client probe).
  • GET /api/v1/events/stream[?sessionId=…] — SSE stream of domain events (MESSAGE_APPENDED, TOOL_CALL_COMPLETED, SESSION_STATE_CHANGED, …).

All /api/v1/* endpoints require the configured bearer token when authentication is enabled (development mode without a token is loopback-only).
